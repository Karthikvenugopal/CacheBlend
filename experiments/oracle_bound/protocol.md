# Bounded actual-repair oracle diagnostic

This is a separate development-only diagnostic, not a new selector or a benchmark expansion. The prior selector remains rejected; validated source and all earlier results remain unchanged. No generalization, speedup or novelty claim is permitted.

Before inference, fix the 12 candidate edits in `candidates.json`, their order, prompt format, greedy limit (24 tokens), seed 17, four CPU threads, float32 native eager TinyLlama and the locally cached model revision. Do not add or rewrite candidates after observing outputs. Six compact templates are tested in both edit directions. The longer answer limit addresses the prior pilot's truncation limitation and applies identically to all new screening/oracle runs; it does not change the earlier pilot.

Retokenize both complete chat prompts independently. Split the identical fresh question from the cached document using tokenizer offsets. Enforce equal document token counts, identical query tokens and at most 16 unchanged suffix positions after the actual edit envelope. Unsupported candidates are retained with explicit reasons and are not silently shortened. No edit-length shifts are supported.

Screen all 12 candidates, retaining original clean, edited full recomputation and mandatory-edit-only answers, token IDs, limits and logit differences. “Unrepaired suffix reuse” means the known edited span is recomputed while every downstream document KV state stays old; the question is always fresh. A provisional qualifier requires an edited full answer containing the correct requested value without the competing old value, and an edit-only answer explicitly giving the old competing value without the new one. Ambiguous answers and nonanswers do not qualify as established factual regressions. Manually review all outputs before the oracle stage; record any formatting, negation or semantic ambiguities separately. Original clean-model correctness is reported but is not an additional hidden screening requirement.

If no cases establish a clean-correct/reuse-wrong pair, stop: the setup as screened is unsuitable for evaluating factual repair. Do not search further prompts, change decoding or optimize a selector to force a positive result.

If cases qualify, search at most the first two confirmed qualifying cases in fixed candidate order, retaining all screened outcomes and recording any additional qualifiers as unsearched under the compute bound. For each selected case, enumerate every one-token and two-token subset of the **complete** unchanged downstream document suffix, including its last token. At a suffix length of 16 this is 16 + 120 = 136 choices per case, at most 272 total. This is exhaustive over token positions at these budgets; it is not an upper bound over other budgets, layer schedules or repair operators.

Use actual layer-wise target-model recomputation from the same independently owned old cache, always refreshing the edited span. No states may be transplanted from a clean oracle cache. The local control uses the first one/two suffix positions at the same budget. Query processing and answer decoding are identical for all choices. Verify full downstream recomputation against the native edited reference before enumerating; stop on an unexplained mismatch. Verify screen-answer reproducibility on the selected cases.

Labels do not guide enumeration or stop the search early. Generate and retain every support's answer first; afterward use labels to identify all correcting supports, best achievable factual success and whether it exceeds local repair at each budget. Retain all ties and failures, not just the winning support. Describe useful positions in actual token coordinates and their textual dependencies; one-token results provide leave-one-out controls for two-token successes. Statistical generalization and deployability do not follow from label-selected maxima.

Only useful oracle headroom beyond local repair, together with a concrete dependency explanation, could justify considering further method development. Otherwise do not recommend another selector. Resource counts are execution bounds, not performance results.

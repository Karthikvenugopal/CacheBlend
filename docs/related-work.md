# Scope review — 2026-11-08

The broad edit-repair proposal is already covered. This repository is a small independent inference study informed by CacheBlend, **not a reproduction of its selective fusion algorithm or its reported speedups**. The first increment establishes the cache interface and reference paths needed before attempting that reproduction. No novelty is claimed.

| Work | Established contribution relevant here | Distinction from this increment |
|---|---|---|
| [CacheBlend, v3 (2025)](https://arxiv.org/html/2405.16444v3), §§3–7 | Combines independently cached text chunks in a new causal context. Selectively recomputes token states, uses shallow-layer KV deviations and gradual filtering, corrects positional embeddings, and pipelines loading with computation. | It is a chunk-fusion method, not an existing algorithm for synchronizing a document cache after an in-place edit. Its approximate quality preservation is not exact logit equivalence. |
| [Cache-Craft (2025)](https://arxiv.org/html/2502.15734v1), §§3–5 | Stores contextualized chunk-cache versions. Uses inter/intra-chunk attention and prefix overlap/order to estimate reusability and recomputation budgets; repairs highly contextualized tokens and terminates work on unfocused chunks. | Context-dependent repair and adaptive selection are established ideas. This does not by itself establish correctness after a source edit. |
| [Prompt Cache (2024)](https://arxiv.org/abs/2311.04934) | Schema-defined reusable modules with positional accounting. | Modular prompt reuse differs from arbitrary edited-document consistency. |
| [EPIC, v3 (2025)](https://arxiv.org/html/2410.15332v3), §§3–5 | Position-independent caching; LegoLink repairs document-start attention sinks with a small fixed token set. | Boundary repair is prior work, not a novel mechanism to claim here. Earlier EPIC versions use different names; this note uses v3. |
| [KVLink (2025)](https://arxiv.org/abs/2502.16002) | Independent document encodings, position adjustment, trained link tokens and mixed-data fine-tuning. | Adds training rather than establishing training-free edit repair. |
| [ProphetKV (2026)](https://arxiv.org/abs/2602.02579) | Query-guided token selection and layer-wise attention fusion for RAG cache recomputation. | Query/dependency-based selection is already explored. |
| [Models Take Notes at Prefill (2026)](https://arxiv.org/html/2606.17107), §§3–4 | Studies downstream cached conclusions, field-only update failures, selective downstream recomputation, and append-only errata; behavior depends on model and reasoning mode. | Direct conceptual overlap with the contextual-dependency question. An appended erratum changes the prompt and is a separate baseline, not identical-prompt repair. |
| [Contiguity, Not Importance (2026)](https://arxiv.org/html/2609.17983v1), §§3–6 | Explicit budgeted in-place KV repair after equal-length edits. Compares contiguous edit-local windows, attention, deviation and structural selection on direct/derived factual edits. Reports loss of local-window advantage when dependent text moves away. Distinguishes oracle-state transplant from deployable recomputation. | **Direct overlap**, including the obvious next local-window experiment. A replication/failure-boundary study is appropriate; claiming this repair mechanism as new is not. |
| [PatchKV (2026)](https://arxiv.org/html/2609.26219v1), §§III–V | Middle-edit prefix/span/aligned-suffix decomposition, offline length-conditioned dirty-window prediction, nonlocal attention blocks, RoPE correction and calibrated transport precision. | **Direct overlap** with selective suffix repair. Its offline profiling and transfer/quantization costs must be included when comparing policies. This project initially excludes those confounders. |
| [Request Order Matters (2026)](https://arxiv.org/html/2610.05833v1) | Persistent approximate caches can produce history-dependent answers; studies document-aligned versus scattered repairs. | Fresh independently owned original caches here deliberately isolate a single edit. Sequential edit accumulation remains future work. |
| [Where Should a KV-Cache Repair Budget Go? (2026)](https://arxiv.org/abs/2611.06397) | Examines distractor structure and contextual compatibility; reports that actual recomputation and full-state transplantation can behave differently. | The latest search result reinforces that oracle transplant is not a deployable repair or a reliable performance upper bound. |

Reading depth: CacheBlend and Cache-Craft design, implementation, evaluation setup/results; PatchKV and Contiguity repair interfaces, selection, costs and evaluation; EPIC v3 design; Notes editing sections; remaining entries are abstract-level screening. This is a dated review, not an exhaustive novelty certificate. No external claims were independently replicated here.

Implementation inspection: the current [LMCache documentation](https://github.com/LMCache/LMCache/blob/dev/docs/source/kv_cache_optimizations/cacheblend.rst) points to a multiprocess blend engine and separates legacy in-process support. The version-pinned [v0.3.7 LMCBlender](https://github.com/LMCache/LMCache/blob/v0.3.7/lmcache/v1/compute/blend/blender.py), `process_qkv`, compares float32 squared key differences at configured check layers, sorts top-k positions, narrows Q/K/V/residual, and updates selected cached rows. `blend_layer` interleaves layer-wise retrieval and computation. Its `blend` path explicitly uses CUDA. The implementation's configurable check-layer/top-k behavior should not be conflated with every detail of the paper's gradual-filtering scheme.

The current [retrieve implementation](https://github.com/LMCache/LMCache/blob/dev/lmcache/v1/multiprocess/modules/blend/retrieve.py) plans transfer, re-RoPE and scatter, while [rope.py](https://github.com/LMCache/LMCache/blob/dev/lmcache/v1/multiprocess/modules/blend/rope.py) tracks model-specific rotation geometry. These moving `dev` links were inspected on the review date; the older tagged blender provides the stable selection reference. LMCache was not installed or executed: the initial CPU adapter avoids its serving integration and custom GPU kernels.

Narrowed question: on an unquantized small causal Llama, how do edit location, downstream dependency distance and irrelevant intervening text affect distribution drift and answer fidelity when reusing a suffix? Can a replicated repair baseline reduce those errors at a measured total cost? Equal token lengths isolate contextual effects. Development cases identify harness/failure issues; held-out cases must remain unused until the mechanism and metrics are frozen. TinyLlama failures may require a stronger *locally available* model before an efficacy claim is meaningful.

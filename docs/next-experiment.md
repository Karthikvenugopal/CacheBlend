# Proposed next increment — not implemented

Observation: naive reuse introduces next-token max-logit deviations of 0.13–0.74 and KL of roughly 0.0006–0.0038 on development examples. Two of six greedy continuations differ. Those differences do **not** demonstrate new factual errors: on the shipping question full recomputation itself is unhelpful, and the derived question changes wording while retaining Lima. Four identical continuations also conceal distribution drift. This motivates a distribution-fidelity experiment, not a claim of answer recovery.

Replicate an **edit-local contiguous window** baseline: recompute from the first differing token through `edit_end + w`, then keep the remaining suffix stale and replay the final prompt token. Signal: token distance from the actual edit, with fixed `w ∈ {0, 4, 8, 16, 32}` chosen on development only. This requires no attention extraction or oracle KV comparison to choose positions. Added computation is at most w tokens through all layers, plus prefix copying, suffix splicing and the final replay already present in the naive baseline. Longer queries still attend to the retained prefix, so token count alone does not specify FLOPs or latency.

Why it may help: positions immediately downstream can carry contextualized representations of the edited fact. Recomputing an uninterrupted causal segment builds fresh dependencies within that window. It cannot guarantee restoration of more distant dependent states or of factual accuracy. This is a replication of EditLocal in [Contiguity, Not Importance](https://arxiv.org/html/2609.17983v1), with related locality in [PatchKV](https://arxiv.org/html/2609.26219v1); it is not a new mechanism.

Freeze development fixtures, prompt format, seed, tolerance, budget and scoring before using `examples/heldout.json`. Keep direct fact lookups separate from derived lookups and unchanged-answer controls. Extend the next development suite with controlled dependency-distance and distractor variations before freezing; TinyLlama must solve each clean task before that task can demonstrate repair efficacy. Preserve all baseline failures in the report and show both unconditional results and results conditional on correct clean answers. The existing three held-out fixtures are a smoke holdout, too small for a research efficacy claim; a larger disjoint evaluation would need separate approval after this increment.

For the eventual comparison: full recomputation, exact-prefix, naive (w=0), and each frozen window budget. At matched work budgets compare against a seeded random position selector only once a correct scattered-recompute adapter exists; don't fake one by transplanting clean KV. Report per-case next-token KL/TV, logit error, teacher-forced answer probabilities, greedy agreement, manually audited known-answer correctness and change/invariance accuracy. Include cases where the edit and dependent evidence are far apart to test whether locality is an example-specific heuristic.

Measure repeated CPU end-to-end runs with randomized method order and cache-copy/selection/splice/decode overhead. Report original-cache construction separately and also include it when amortization is evaluated. Treat model loading and tokenization consistently across methods. CUDA/MPS performance requires measurements on those backends; no GPU speed claim follows from the current CPU observations. Stop if drift improves without answer utility, overhead outweighs savings, or clean-model failures make the task uninformative.

Potential later contribution: a measured failure-boundary map and a justified policy decision under those boundaries. A new selection mechanism is not yet justified by the observed evidence. Recheck recent work before describing any later mechanism as novel.
